Architectural Overview & Design Principles

OpenSourceLens is architected as an enterprise-grade multi-tier web application adhering to the classic Model-Template-View (MTV) design pattern, fortified with a decoupled service orchestration layer and a vectorized analytical processing pipeline.

1. Decoupled Service Layer

Views remain thin controllers. All external GitHub API ingestion, data normalization, database synchronization, and caching decisions are orchestrated inside dedicated service singletons (GitHubService, AnalysisService, RepositoryService).

2. Deterministic Analytics

All metric computations are handled exclusively by AnalyticsEngine using vectorized Pandas DataFrames. Zero analytics are simulated, fabricated, or randomized.

3. Immutable Snapshots

Each analysis run creates a dedicated, immutable RepositoryAnalysis snapshot record inside an isolated atomic database transaction (transaction.atomic), preserving historical truth and auditability.

Request Lifecycle: From Repository URL to Health Score

Every repository analysis follows an exact 9-step execution pipeline guaranteeing data provenance and transaction integrity:

Step 1

Input Validation

Parses GitHub URLs or shorthand (owner/repo) with strict regex checks, stripping trailing slashes and invalid characters.

Step 2

Identity Canonicalization

Resolves transfers and aliases (e.g. facebook/react $\to$ react/react) so entities map to canonical records.

Step 3

Cache Verification

Checks local PostgreSQL snapshots. If fresh within 60 minutes and refresh=False, serves instantly with zero API requests.

Step 4

Outbound Ingestion

Issues paginated HTTP calls with Bearer authentication for metadata, languages, commits, issues, PRs, and contributors.

Step 5

Data Cleansing

Filters pull requests out of issues, parses timestamps with UTC safety, and prunes stale records outside the window.

Step 6

Atomic Persistence

Saves entities and creates an immutable RepositoryAnalysis snapshot record inside transaction.atomic().

Step 7

Statistical Modeling

Pandas calculates active-day vs calendar-day commit velocities, median resolution times, and contributor HHI concentration.

Step 8

Health Scoring

Computes the composite 5-pillar health index (0–100) and assigns an analytical maintainability tier.

Step 9

Dashboard Presentation

Renders interactive Chart.js visualizations, metric cards, and transparent data coverage bounds.

Relational Data Model & Snapshot Immutability

The OpenSourceLens database schema is strictly normalized around the Repository root aggregate entity, maintaining relational integrity across child entities and immutable audit snapshots: 

Repository (Root Aggregate: owner, name, full_name, stars, forks, license, topics)
   │
   ├── Contributor (Foreign Key: username, contributions, avatar_url, profile_url)
   ├── CommitActivity (Foreign Key: date, commit_count)
   ├── Issue (Foreign Key: issue_number, title, state, created_at, closed_at)
   ├── PullRequest (Foreign Key: pr_number, title, state, created_at, merged_at)
   ├── Language (Foreign Key: language, bytes, percentage)
   └── RepositoryAnalysis (Foreign Key: immutable snapshot_payload, health_score, 5 pillar scores)

Why Immutable Snapshots?

  • Longitudinal Trend Tracking: Plotting health score trajectories requires historical snapshots that never mutate when subsequent analyses run.
  • Reproducibility: Prior audits can be re-inspected exactly as they were evaluated at the time of submission.
  • Window Isolation: A 30-day snapshot is completely isolated from a 90-day or 365-day analysis on the same repository.

Data Protection & ACID Guarantees

  • Atomic Transactions: Database synchronizations run inside transaction.atomic(); partial or interrupted ingests rollback cleanly.
  • Non-Destructive Overwrites: A failed live GitHub fetch (due to network drops or rate limits) never deletes or corrupts existing snapshots.
  • Audit Logs: Complete serialized payloads (snapshot_payload JSONField) are saved alongside scalar metric columns.

1. Activity Score

25% Weight

Multi-signal development cadence across four explicit components (0–100 points):

  • Recency (40%): Days since last push (≤3d: 40 pts, ≤7d: 36, ≤14d: 32, ≤30d: 28, ≤60d: 22, ≤90d: 16, ≤180d: 10, >180d: 4)
  • Frequency (30%): Commit volume scaled against analysis window calendar days
  • Consistency (15%): Ratio of active commit days to total calendar days in window
  • Trend (15%): Velocity momentum comparing recent vs prior half of window

2. Issue Management Score

20% Weight

Measures triage velocity, resolution rates, and backlog control (0–100 points):

  • Sample Resolution Rate (45%): (Closed Issues / Analyzed Issues) × 45
  • Turnaround Velocity (35%): Evaluated via median resolution time (≤24h: 35 pts, ≤72h: 28, ≤1wk: 22, ≤1mo: 15, >1mo: 8)
  • Backlog Hygiene (20%): Penalty applied for unresolved issues open >90 days

3. PR Activity Score

20% Weight

Quantifies contribution throughput and merge velocity within the window (0–100 points):

  • Analyzed Merge Efficiency (50%): (Merged PRs / Analyzed PRs) × 50
  • Turnaround Velocity (35%): Median merge turnaround in hours/days (≤24h: 35 pts, ≤72h: 28, ≤1wk: 20, ≤1mo: 12, >1mo: 5)
  • Throughput Volume (15%): PR submission cadence scaled across the window period
  • Explicit caveat: Code review comment depth is not collected or simulated.

4. Contributor Diversity

15% Weight

Assesses distribution and concentration among analyzed contributors (0–100 points):

  • Contributor Base Depth (40%): Evaluates count of analyzed contributors (≥20: 40 pts, ≥10: 32, ≥5: 24, ≥3: 16, ≥2: 10, 1: 4)
  • Herfindahl-Hirschman Index (HHI) (40%): HHI = Σ (share_i)² (<1500: 40 pts, <2500: 30, <4000: 20, ≥4000: 10)
  • Lead Contributor Share (20%): Dominance of top author (<35%: 20 pts, <50%: 16, <70%: 10, ≥70%: 4)
  • Scope: Concentration measured among analyzed contributors returned by GitHub API.

5. Maintenance & Hygiene Score

20% Weight

Verifies metadata standards, licensing, and repository status via direct 0–100 normalization:

License (30 pts): Valid SPDX open-source license detected
Active Status (25 pts): Non-archived and maintainable
Description (20 pts): Meaningful repository description
Topics (15 pts): Discoverability topic tags defined
Branch (10 pts): Standard default branch (main/master)
Health Score Interpretation Tiers:
85–100 Excellent: Highly active, structured triage, resilient maintainer base.
70–84 Good: Consistent development cadence with manageable backlog.
50–69 Moderate: Slower review turnaround or higher maintainer dependency.
0–49 At Risk: Stagnant commit cadence or elevated maintenance risk.
Methodology Notice: Health score classifications are application-defined comparative diagnostic indicators designed to highlight operational trends. They are not universal software-quality certifications.

GitHub API Architecture & Rate-Limit Resilience

OpenSourceLens implements an enterprise-grade GitHub API client architecture designed for strict security, rate-limit awareness, and zero-data-loss resilience:

Centralized Authentication

All external requests pass through a centralized GitHubService singleton using application/vnd.github+json and GitHub API version 2022-11-28.

  • Authenticated Tier: 5,000 requests/hour via Personal Access Token (PAT).
  • Unauthenticated Tier: 60 requests/hour shared across local IP.
  • Zero Token Leakage: Secrets are strictly read from .env and never logged, rendered in HTML/JSON, or committed to Git.

Snapshot-Aware Fallback

If live GitHub requests are rate-limited or interrupted by network timeouts, OpenSourceLens automatically falls back to the most recent stored snapshot:

  • Non-Destructive: Failed live fetches never overwrite or erase valid stored snapshots.
  • Prominent Notice: Telemetry dashboards inform users when displaying stored snapshots due to active rate limits.
  • Exact Reset Telemetry: Displays UTC reset timestamps and countdowns derived directly from GitHub response headers.
CLI Health Check Command: Built-in Diagnostic
python manage.py check_github_api
Safely validates token status, remaining quota, reset time, and API connectivity without exposing credentials.

Data Quality, Sampling & Analytical Scope

In accordance with academic rigor and data provenance standards, OpenSourceLens makes all sampling bounds transparent:

  • API Sampling vs Total Counts: GitHub REST API queries analyze bounded batches of recent commits (up to 100–250 per window), issues (up to 50–150), and PRs (up to 50–150). Metrics reflect this analyzed sample within the selected window, clearly denoted as "Analyzed Commits" rather than total repository history.
  • Analysis Window Sensitivity: Velocity, turnaround, and cadence metrics depend directly on the chosen window (30D, 90D, 6M, 1Y). An active repository evaluated across 30 days reflects recent sprint activity, whereas a 1-year evaluation reflects long-term sustainability.
  • Contributor Concentration Boundaries: Contributor rankings and Herfindahl-Hirschman Index (HHI) concentration scores evaluate the top 30 recorded contributors returned by the GitHub API.
  • Data Privacy: OpenSourceLens exclusively ingests public repository metadata. No private repository content, personal passwords, or private keys are collected or stored. Configured GitHub tokens remain strictly server-side.
